# 05 — Миграции и обслуживание БД

Статус: **проверен с ограничениями**. Предпосылки: 04; зафиксированы схема и transactional boundaries.

## Цель и вопросы

Проверить соответствие схемы, historical rows и безопасную последовательность обслуживания без автоматического запуска.

## Компоненты и зависимости

[SQLite migrations](../../../adapters/AgentBridge.Persistence.Migrations.Sqlite), [PostgreSQL migrations](../../../adapters/AgentBridge.Persistence.Migrations.PostgreSql), factories, AgentBridgeMigrationsHistory, DatabaseMaintenanceRegistrationExtensions/DatabaseBackupOptions. EFCoreLibrary maintenance: IDatabaseMaintenance и coordinator/provider modules. Тесты ProviderDesignTimeTests, DatabaseMaintenanceTests, Integration/MaintenanceIntegrationTests, DialogSettingsIntegrationTests.

## Способ проверки и границы

Сверить InitialAgentBridgeSchema → AddDurableToolAttempts → AddDialogSettings с model snapshots обоих providers, отдельным __AgentBridgeMigrationsHistory и шестью mapped таблицами. Проверить nullable legacy значения без выдуманной provenance. Для разрешённых C-сценариев: Up/Down/Up на копии, сохранение payload, отсутствие pending drift, Missing против auth failure, initialization против update, no-pending без backup, backup до DDL, отказ backup/DDL, poisoned gate, отмена/cleanup. Проверить SingleInitializer как обязанность приложения, отдельный scope, явную backup retention и restore в другую БД с сопоставлением схемы/данных.

## Разрешения

A; metadata/fake maintenance — B; любые БД/SQL/Up/Down/native backup/pg_dump/restore/процессы — C. Generated migrations не редактировать и новые не создавать. Общие правила — [методика](Methodology.md). Исправления и изменение тестов запрещены.

## Доказательства и запись результатов

Карта migrations и данных до/после, порядок обслуживания, receipt против фактической восстановимости, отдельные ограничения каждого provider. Заполнить [шаблон отчёта](Methodology.md#шаблон-результатов-этапа) ниже; проблемы заносить в [Findings](Findings.md), указывая ID, категорию, достоверность, серьёзность и ограничения. Наличие проблемы не препятствует завершению исследования.

## Критерий завершения

Схема, legacy совместимость и все ветви обслуживания получили результаты либо объяснённые пропуски. Пропуск записать с причиной и влиянием; не считать его успешной проверкой.

## Что этап не подтверждает

SQL Server/MySQL, работоспособность multi-instance SingleInitializer без приложения, автоматическое удаление backup и восстановление любой production-БД.

### Кандидаты находок и вопросы

**[ABQA-006](Findings.md#abqa-006) — отказ discovery после CREATE не отравляет gate.** Категория: дефект реализации зависимости; **подтверждено статически**, runtime не воспроизведён. **S2**: нарушена обязательная блокировка ключевого maintenance-сценария после незавершённой первой установки; data loss не установлена.

- Контракт: spec:731–733, отказ после начала установки запрещает дальнейшее обслуживание тем же gate. [DatabaseMaintenance](../../../../work/EFCoreLibrary/maintenance/EFCoreLibrary.Maintenance/Coordination/DatabaseMaintenance.cs), ChangeAsync:46–56 успешно Create/Inspect/Pin/binding, затем заменяет Stage=Initialization на Discovery; PendingAsync:56 может выбросить exception/OCE. ExecuteAsync:102–108 проверяет только **текущую** Stage, не факт начатого CREATE.
- Минимальный статический путь: Missing → успешный CREATE → успешные binding/pin → PendingAsync throws обычную ошибку, pin cleanup успешен. Stage=Discovery, code=ConnectionFailed, condition107=false; lease освобождён113, gate не poisoned. Следующий Inspect/Update того же root допускается к provider вместо GatePoisoned. То же при фактической отмене в discovery; pre-migrate Inspection:68–71 имеет аналогичную потерю признака initialization.
- Ограничение/проверка: состояние реальной DB и успешность повторного update неизвестны. Будущий B-сценарий — failure/OCE после успешного create в pending и final target recheck, наблюдение отсутствия provider calls следующего scope; C — только своя provider DB. Existing tests NewDatabaseIsInitializedExplicitly:67–75/InitializationCollision:203–212 не проверяют этот промежуток; отсутствие теста не основание дефекта. Связь:14/15, не дубль ABQA-005; устойчивый ID выдаёт координатор.

**[ABQA-007](Findings.md#abqa-007) — вторичный cleanup теряет первичный безопасный код.** Категория: дефект реализации зависимости; **подтверждено статическим порядком исключений**, достижимость конкретного driver/native/process отказа не воспроизведена. **S3**: теряется причина для диагностики/recovery; poison и запрет DDL в основном примере сохраняются, утечка/потеря данных не заявляются.

- Контракт: spec:750–751 и EF `C/Errors/AGENTS.md`: первичный код должен сохраняться при secondary cleanup. ChangeAsync:53–79 использует await using pin без capture primary; [EfMigrationOperations.ConnectionLease.DisposeAsync](../../../../work/EFCoreLibrary/maintenance/EFCoreLibrary.Maintenance/EfCore/EfMigrationOperations.cs):40–43 заменяет close exception на `MaintenanceException(CleanupUnconfirmed)` без PrimaryError. ExecuteAsync:111 копирует уже пустой PrimaryError.
- Контрпример по коду: BackupAsync бросает `MaintenanceException(BackupNotConfirmed)`, затем CloseConnectionAsync бросает. Dispose заменяет pending exception; наружу CleanupUnconfirmed/PrimaryError=null вместо сохранённого BackupNotConfirmed. Gate poisoned107–108, migrate не вызывается. Без secondary failure typed code сохраняется — негативная граница.
- Та же потеря первичной причины видна в [BackupProcessRunner.RunAsync](../../../../work/EFCoreLibrary/maintenance/EFCoreLibrary.Maintenance/Processes/BackupProcessRunner.cs):29–35 (catch без capture → unknown stop → новый CleanupUnconfirmed) и SqliteBackupStepper:32–35 (finish failure заменяет pending error/OCE). Это один класс primary/cleanup preservation, не отдельные дубли. Workspace.Dispose(failure):101–104 сохраняет primary только когда он ещё передан; уже потерянный pin/process/native код не восстанавливает.
- Будущий B: existing fake BackupAction=typed failure вместе с FailCleanup=true; separate process/native fake primary+stop/finish failure. В T/DatabaseMaintenanceTests:175–194 cleanup проверен отдельно, а backup-cleanup передаёт готовый primary из fake — не proof комбинации pin. Тест/репродуктор не создан и не запущен; новый case требует отдельного поручения. Связи14/15; это другая первопричина, чем ABQA-002 HTTP disposal, его runtime-статус не повышается.
