# 11 — Полный ход агента и восстановление

Статус: **проверен с ограничениями**. Предпосылки: 07–10; разобраны transport, context, persistence и tools.

## Цель и вопросы

Проверить целый путь обращения, согласованность сохранения и отсутствие автоматического повторного исполнения известных попыток.

## Компоненты и зависимости

[AgentRunner](../../../Application/AgentRunner.cs), [AgentRunSession](../../../Application/AgentRunSession.cs), AgentRunScope, AgentRunResult, IDialogToolAttemptWriter и DialogToolAttemptUnitOfWork. Тесты AgentRunnerTests, Integration/AgentRunnerIntegrationTests, CrossComponentIntegrationTests/CrossComponentFixture.

## Способ проверки и границы

Проследить чтение → pinned settings/access → providers один раз → atomic begin → compact/full guard → model step → durable Started → handler → atomic outputs/journal → terminal save. Негативные точки: отказ каждой записи, старый TurnId/legacy без journal, restart после Started, потеря acknowledgement после commit, partial call, parallel tools failure, expiration/delete/recreate во время ожидания. Проверить matching StepId для LastResult, successful compact token при следующем exception, запрет refresh/retry после blocked storage. Completed требует terminal save; late Canceled может сосуществовать с уже сохранённым Completed. Новый TurnId не считать способом recovery неизвестного действия.

## Разрешения

A; fake store orchestration — B; настоящий persistence/restart и controlled commit faults — C; живой model endpoint и crash процесса — отдельные D/C-разрешения. Общие правила — [методика](Methodology.md). Исправления и изменение тестов запрещены.

### Trace версий и границы recovery

Статический пример, не наблюдение runtime: исходная revision `r`, новый turn; Begin→`r+1/InProgress`; первый model append→`r+2/Completed report`; Started→`r+3/Started`, затем один разрешённый handler; outcomes→`r+4/Succeeded+output`; следующий model append→`r+5`; отсутствие pending calls→terminal `r+6/Completed`, TerminalSaved=true. Компактные saves/дополнительные Started добавляют собственные revisions; parallel Starts сериализуются. Контракты: R:73–152, S:31–65, P/DialogTurnUnitOfWork.cs:90–102 и P/DialogToolAttemptUnitOfWork.cs:89–96.

Обрыв после сохранённого Started оставляет barrier, без outcome нельзя предполагать rollback внешнего действия. Если outcomes commit состоялся, но ответ writer потерян, persisted state может быть Succeeded+output, а runner token ещё `r+3`; run blocked и ничего не перечитывает ради продолжения. Повтор того же TurnId отклоняется даже после terminal. Новый TurnId — отдельный сценарий, не средство доказать исход прежнего действия. Exactly-once внешнего бизнес-действия библиотека не обещает.

### [ABQA-009](Findings.md#abqa-009) — cleanup-only OCE маскируется caller cancellation

- **Категория / достоверность / серьёзность:** дефект реализации; **подтверждён статическим контрпримером**, S3 — теряется техническая ошибка cleanup и её причина, без доказанного повторного действия, потери данных или утечки ресурса.
- **Нарушенный контракт:** main spec:391 запрещает маскировать unexpected exceptions ожидаемым отказом; R:14–15 и техничка20:40 требуют распространить неожиданный exception после honest finalization. Отмена caller сама по себе не доказывает происхождение exception из DisposeAsync, который не получает caller token.
- **Достижимый вход без запуска:** successful Begin, successful generation с pending call, successful Append port. Caller отменён перед завершением append scope; его `DisposeAsync` выдаёт **отдельную** `OperationCanceledException` с токеном, отличным от caller (например, default). Operation в A:13 уже успешна, `primary=null`; A:17–20 пропускает cleanup OCE наружу. S:105–106 уже захватил token/step; S:110–113 блокирует writes. R:155–157 смотрит только `caller.IsCancellationRequested` и возвращает FinishAsync(Canceled). R:174–175 видит blocked: итог Canceled/TerminalSaved=false/принятый step, Error=null при отсутствии прежнего typed refusal. Сам cleanup exception и его token наружу не доходят. Handler0, refresh0, повторных writes0 по этому пути.
- **Evidence:** HEAD41072fc, R:120,155–175; S:94–113; A:12–20. Existing T:582–597 допускает static configuration `AfterWrite` отменяет caller на append, `ThrowScopeAt=append`, `ScopeException=OCE(default)`; соответствующий invocation/assertion **не добавлялся и не выполнялся**. T:457–466 проверяет IOException disposal отдельно, не это сочетание. Основание кандидата — control flow, отсутствие теста не основание.
- **Негативные контроли:** caller не отменён→OCE идёт R:159–164 и распространяется; IOException disposal при отменённом caller также идёт general catch. **Primary+cleanup AggregateException** из A:18–20 broad OCE catch не поглощает и распространяет оба exception. Обычная caller cancellation при успешном cleanup должна оставаться Canceled; successful terminal без cleanup exception сохраняет documented late-cancel результат T:340–350.
- **Влияние / ограничения / связи:** consumer может принять cleanup failure за штатное пользовательское прекращение и потерять диагностику. Blocking сохраняется; leak/replay/real provider достижимость не установлены. Не дубль ABQA-002 (HTTP disposal), ABQA-007 (maintenance primary code) или ABQA-008 (empty SSE EOF). Для независимого B-подтверждения нужен отдельный case указанной комбинации с тремя контролями; новых tests/harness нет, готовой команды такого case нет. Передать14/15, координатор присвоил устойчивый ID ABQA-009.
