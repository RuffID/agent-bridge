## Разрешения

Сейчас выполняется только подготовка документов. Даже ранее разрешённый исторический запуск не разрешает повторить его в этом аудите.

| Уровень | Что допускает проверка | Что требуется |
| --- | --- | --- |
| A — статическое чтение | Файлы, локальные ссылки, UTF-8, история Git, анализ существующих тестов и логов | Поручение на соответствующий этап; только read-only Git status/diff/log/show/rev-parse |
| B — локальное исполнение без интеграций | Сборка конкретного проекта, существующие изолированные тесты, локальная CLI validation | Отдельное разрешение на точную команду и проверенный проект/исполняемый файл; сейчас запрещено |
| C — реальное окружение | SQLite, PostgreSQL, Docker, SQL, migrations Up/Down, backup/restore, native DLL, процессы | Отдельное разрешение на команды, собственные тестовые ресурсы, границы записи и очистку |
| D — внешний контракт | Живой codex-lb/HTTP, авторизация upstream, hosting и приложение | Отдельное разрешение на endpoint, аккаунт, данные, расходы и точные операции |

B не включает SQLite in-memory, EF InMemory, TestServer, WebApplicationFactory, Docker, сеть и дочерние бизнес-процессы. Restore может обращаться к сети; его нельзя незаметно включать в локальную проверку. Перед B/C читать действующие AGENTS, csproj, ancestor build/import-файлы и профильные скиллы. EFCoreLibrary имеет GeneratePackageOnBuild=true: в согласуемых restore/build/test нужен -p:GeneratePackageOnBuild=false. Не собирать solution автоматически.

Запуск существующих тестов не разрешает их изменять. Если сценарий требует нового harness или изменения теста, записать пробел и остановить именно эту проверку; разработка средства воспроизведения требует отдельного поручения вне текущих границ. Автоматические build/test outputs допустимы только в отдельно согласованных временных каталогах после разрешения запуска; ручное изменение generated-файлов запрещено.

Для persistence сначала проверить traits и opt-in в исходниках. Изолированный фильтр — Dependency!=Database; интеграционный — Dependency=Database с явными параметрами выделенного окружения. Это элементы будущей команды, а не готовое разрешение. Список классов/методов и точную команду сформировать перед запуском, сверив актуальный код.

OpenSpec CLI ранее отсутствовал. Не устанавливать его. Если запуск отдельно разрешён и CLI доступен, использовать specs/change validation с нужным strict-режимом по доступному CLI. Записать команду, версию, вывод и exit code; чтение Markdown validation не заменяет. Непроверенные changes не архивировать.

## Что считать доказательством

1. Контракт: заголовок требования, публичный API, согласованное правило; версия источника.
2. Статический путь: вход, условия, ветви, сохраняемые данные, выход; файл, метод и строки на зафиксированном commit.
3. Воспроизведение: минимальные данные, точный вызов, ожидаемый и фактический результат, повторяемость.
4. Граница: настоящие компоненты и заменённые заглушками; окружение, версии, время, пропуски.

Статически доказанное противоречие можно подтвердить без запуска, явно указав способ. Возможный runtime-эффект без воспроизведения остаётся подозрением. Отсутствие теста — пробел проверки, а не доказательство дефекта.

HTTP fixtures не подтверждают живой codex-lb. SQLite/PostgreSQL не подтверждают SQL Server/MySQL; последние не являются провайдерами AgentBridge. Fake writer не подтверждает атомарность БД. Новый DI container не равен аварии ОС. Синтетическая потеря acknowledgement не равна реальному обрыву сети. Compile-check и PE/XML не доказывают runtime/native загрузку или отображение XML конкретной IDE. Локальный tokenizer не доказывает server billing count и полный размер opaque-контекста.

Исторический TRX относится к своему коду и окружению. Проверять наличие и происхождение файла, не запускать повторно ради числа. Пересекающиеся наборы и повторы не суммировать. Удалённый/отсутствующий артефакт обозначать как недоступный; цитируемый отчёт не объявлять заново воспроизведённым результатом.

## Шаблон результатов этапа

- Дата, исполнитель, HEAD AgentBridge и зависимостей, исходный status/diff.
- Вопрос → требование → файл/метод → способ A/B/C/D.
- Сценарий: предусловия, вход, граница или отказ, ожидаемое поведение.
- Факт: просмотренный путь либо точная разрешённая команда, exit code и артефакт.
- Вывод: подтверждено / опровергнуто / недостаточно данных / не проверено.
- Findings: ID или «новых записей нет»; не придумывать проблемы.
- Ограничения, причины пропусков и влияние на следующий этап.
- Статус этапа и проверка неизменности недокументальных файлов.

В реестре не хранить ключи, подключения, raw envelopes, персональные сообщения и exception dumps. Использовать обезличенный минимальный пример, безопасные коды и ссылки на доступные доказательства. Исправления не выполнять и не маскировать новой бизнес-политикой.
