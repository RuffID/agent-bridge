# Препятствия этапа03 и адаптация к существующему sub2api

Дата проверки: 2026-11-07. [Результаты](results.md) · [Вопросы T01–T05](../open-questions.md). Это статическое evidence локального checkout, без live HTTP/OAuth и без Git revision.

**Текущая граница:** sub2api не дорабатывается. [Предложение серверного расширения](server-contract-proposal.md) отклонено и не является путём снятия блокировки. Продолжение относится только к AgentBridge и использованию existing server routes/configuration; отсутствие выдуманных budget/capabilities и сохранность canonical данных остаются обязательными. Требование no-client-retry не распространяется автоматически на внутренние server retries. T01/T05 не закрываются одним изменением направления.

## Проверенная версия и происхождение

Файл [VERSION](../../../../../sub2api/backend/cmd/server/VERSION) содержит `0.2.19`; SHA256 `efb53e7bfd5da3c290cea3bba09b00ec3011b2637638142a816fd27f9e029c51`. Это версия исходников, а не доказательство версии целевого deployment. Повторно проверены size/SHA256 всех28 sub2api entries [описи01](../01-contracts/source-evidence.json):28 совпадений,0 изменений. Поэтому [матрица01](../01-contracts/wire-matrix.md) и её синтетические fixtures сохраняют указанное происхождение. Исторические файлы01–02 не исправлялись.

В `backend` и `docs` sub2api не найдено `input_context_window`. Публичный route `/v1` и query `client_version` не задают versioned семантику входного бюджета. В [routes/gateway.go](../../../../../sub2api/backend/internal/server/routes/gateway.go), `modelsHandler`, непустой client_version только выбирает Codex manifest. В `FetchCodexModelsManifest` [models service](../../../../../sub2api/backend/internal/service/openai_codex_models_service.go) query передаётся upstream, а header Version нормализуется независимо. Подставить `0.0.0` из W02 как рабочую версию нельзя.

При продолжении03 проверка28 hashes повторена:28 совпадений. Дополнительные владеющие источники зафиксированы в [новой описи46 файлов](contract-source-evidence.json), без изменения evidence01. В `backend` и `docs` не найдены также `processing_profile` и `actual_model`; поиск имён сам по себе не доказывает отсутствие эквивалентной гарантии, поэтому ниже прослежены реальные routes/selection/transforms/response paths.

Проверены доступные публичные versioned источники: [release v0.2.19](https://github.com/Wei-Shaw/sub2api/releases/tag/v0.2.19), [Model в этом tag](https://raw.githubusercontent.com/Wei-Shaw/sub2api/v0.2.19/backend/internal/pkg/openai/constants.go), [routes в этом tag](https://raw.githubusercontent.com/Wei-Shaw/sub2api/v0.2.19/backend/internal/server/routes/gateway.go). Публичный поиск по точным именам budget/profile не нашёл дополнительной спецификации. Это ограниченная проверка доступных материалов, не доказательство отсутствия частного контракта и не сверка полного local checkout с release tag/deployment. Live gateway HTTP не выполнялся.

## T01: почему пригодный settings path заблокирован

Обычный каталог [Models/writeOpenAIModelsList](../../../../../sub2api/backend/internal/handler/gateway_handler.go) и [Model](../../../../../sub2api/backend/internal/pkg/openai/constants.go) подтверждают публичные ID. `configuredCodexModelDescriptor/newConfiguredCodexModelDescriptor` из models service добавляют локальные окна/effort. [Metadata projection](../../../../../sub2api/backend/internal/service/openai_codex_model_metadata.go) объединяет разные источники; происхождение каждого поля для generation account публично не доказано. Внутренний [UpstreamModelMetadata](../../../../../sub2api/backend/internal/service/upstream_models.go) содержит MaxOutputTokens, но это не публичный input budget и не гарантия OAuth output control.

AgentBridge реализует ordinary каталог без client_version. Даже присланные похожие metadata/input_context_window игнорируются как неподтверждённые. Safe snapshot: exact ID, HasMetadata=false, окна/лимиты=null, efforts/modalities пусты, флаги false. Пример: context_window272000 и percent95 не дают ни272000, ни258400 входного бюджета. Existing validator возвращает Unsupported, включая ServerValidation policy: ослабления checks нет.

Уточнение: existing manifest уже содержит попытку conservative intersection. `loadCodexGroupCatalogAccounts` использует persistently enabled accounts, включая временно недоступные; но при ошибке `ListModelAvailabilityCandidates` возвращает schedulable subset. `groupCodexModelMetadata/intersectUpstreamModelMetadata` пересекают effort/modalities/context, после чего `applyUpstreamModelMetadataToCodexDescriptor` оставляет некоторые descriptor defaults при неизвестном значении. Это полезная серверная основа, однако нет публичных field-level provenance, привязки к immutable generation pool и доказанного input budget. Отдельная проблема: [resolveOpenAIAccountUpstreamModelForRequest](../../../../../sub2api/backend/internal/service/openai_gateway_scheduling.go) применяет ordinary account mapping, но passthrough generation его пропускает; capabilities нельзя вычислять только через `GetMappedModel`.

Для снятия T01 в исходных границах нужен **доказанный источник бюджета и возможностей, доступный при работе с существующим сервером**. Новые server endpoints/fields не требуются и не планируются. Нужные сведения для проверки достаточности такого источника:

- версия схемы и идентификатор processing profile; exact публичный model ID;
- `input_context_window` с определением доступного входного бюджета и единицами, источник/актуальность; null при отсутствии доказательства;
- точные effort/default и capabilities с происхождением, применимые ко всем аккаунтам, которые профиль вправе выбрать, либо явное ограничение selection pool;
- output limit с отдельной семантикой применимости: для OAuth нельзя обещать enforcement max_output_tokens, который сервер удаляет;
- ошибки unsupported version/profile и правила изменения pool/mapping, исключающие использование устаревших capabilities с другим профилем.

Перечень описывает недостающие доказательства, а не обязательные новые поля sub2api. Отсутствие такого публичного endpoint не означает, что сервер надо расширять. HttpClientLibrary0.0.0.6 позволяет реализованный путь; недостающий HTTP API библиотеки не обнаружен. Пока источник не найден, существующий validator не обходится. Альтернативная клиентская политика бюджета потребует явного изменения требований ядра, а не маскировки числа под объявленную capability.

## T02/T05: обе forwarding ветки и non-stream

В [Forward](../../../../../sub2api/backend/internal/service/openai_gateway_forward.go) после invalid_encrypted_content `trimOpenAIEncryptedReasoningItems` меняет body и запускает повтор. Есть rejected-field recovery и server account failover. [OAuth transform](../../../../../sub2api/backend/internal/service/openai_codex_transform.go) принуждает upstream stream=true и удаляет max_output_tokens, нормализует tools/IDs/instructions/reasoning. [Passthrough body normalization](../../../../../sub2api/backend/internal/service/openai_gateway_request_body.go), `normalizeOpenAIPassthroughOAuthBody`, также принуждает stream=true для generation, store=false и применяет controls/reasoning normalization.

Non-stream приложения остаётся отдельным режимом: `handleNonStreamingResponse/handleSSEToJSON` в [обычной ветке](../../../../../sub2api/backend/internal/service/openai_gateway_response_handling.go) и `handleNonStreamingResponsePassthrough/handlePassthroughSSEToJSON` в [passthrough](../../../../../sub2api/backend/internal/service/openai_gateway_passthrough.go) собирают upstream SSE terminal в JSON, восстанавливают пустой output по deltas. Обе ветки учитывают отсутствующий upstream Content-Type у OAuth; при отсутствии подходящего terminal JSON могут вернуть SSE. Terminal failure/incomplete/cancelled не равен Completed. Обе ветки могут переписать mapped model обратно в original model. Поэтому response.model или HTTP200 не доказывают actual upstream model/неизменность opaque.

Уточнения по enforcement, которых нет в одной настройке passthrough:

- `Forward` выполняет shared reasoning replay/ID normalization и protocol resolution **до** разделения ordinary/passthrough. API-key path может уйти в Chat Completions/Anthropic bridge. `account.IsOpenAIPassthroughEnabled` читает account extra `openai_passthrough`/legacy `openai_oauth_passthrough`; это переключатель ветки, не strict processing contract.
- Ordinary `Forward` предварительно удаляет известные invalid-lineage encrypted items (`stripSessionInvalidEncryptedContentLogged`), помимо уже описанного400 recovery. [deriveOpenAIForwardAttemptBody](../../../../../sub2api/backend/internal/handler/openai_gateway_reasoning_failover.go) при passthrough→ordinary failover удаляет целые encrypted reasoning items перед следующей попыткой. Эти пути не отключаются отсутствием client retry.
- [NewOpenAIGatewayHandler](../../../../../sub2api/backend/internal/handler/openai_gateway_handler.go) использует `MaxAccountSwitches` только при `>0`; ноль оставляет default3. [sameAccountRetryAllowed](../../../../../sub2api/backend/internal/handler/failover_loop.go) при установленном deadline может разрешить retry независимо от обычного pool limit; [newOpenAIAccountFailoverErrorWithClassificationHeaders](../../../../../sub2api/backend/internal/service/openai_gateway_upstream_errors.go) устанавливает deadline для OAuth429. Поэтому pool count0 также не является общим запретом.
- [Rejected-field recovery](../../../../../sub2api/backend/internal/service/openai_responses_rejected_field_retry.go) имеет бюджет до6 repair retries на входящий request, общий между accounts; обе forwarding ветки используют его отдельно от account switch count. Есть agent-task recovery. Подавление failover после semantic output сужает случаи повторов, но не запрещает их до output.

Внутреннее достоверное наблюдение модели **уже есть**: [upstream_response_model.go](../../../../../sub2api/backend/internal/service/upstream_response_model.go) наблюдает raw JSON/SSE до rewrite; [OpenAIForwardResult](../../../../../sub2api/backend/internal/service/openai_gateway_service.go) различает `UpstreamModel`, `UpstreamResponseModel`, `UpstreamResponseModelConflict`. Это не готовая публичная гарантия: observer не блокирует forwarding, нормализует/truncates имена и предпочитает terminal declaration. [UsageLogFromServiceAdmin](../../../../../sub2api/backend/internal/handler/dto/mappers.go) публикует upstream сведения только admin; обычный usage DTO их исключает, что видно в [mapper tests](../../../../../sub2api/backend/internal/handler/dto/mappers_usage_test.go). Нет обязательной доверенной processing metadata в public generation/compact JSON/SSE. Предложение должно развить existing observation, а не изобретать второй observer или обращаться к admin API.

[Локальная regression fixture sub2api](../../../../../sub2api/backend/internal/service/openai_oauth_passthrough_non_stream_test.go) подтверждает наличие проверяемых форм в исходниках; Go-тест здесь не выполнялся, fixture не является живым ответом. Shared writers/framing и codex-lb tests AgentBridge не заменяют Sub2Api gateway acceptance.

Для T05 нужно отделить поддерживаемые existing forwarding paths от случаев потери canonical данных. Server retries/failover документируются как поведение шлюза и сами по себе не являются клиентским повтором или повторным исполнением business tool. Обязательный новый single-attempt API не требуется. Отдельно остаются invalid-encrypted/cross-mode stripping и скрытый model fallback: клиент не может обещать их отсутствие только по `response.model`. Если existing configuration сужает эти случаи, необходимо доказать её применимость ко всему выбираемому pool; один guessed flag или успешная fixture недостаточны. Новые server metadata не планируются; отсутствие достоверной actual model должно оставаться явным ограничением, а не заполняться requested echo.

## T05: compact

В [Responses handler](../../../../../sub2api/backend/internal/handler/openai_gateway_handler.go) есть explicit `/v1/responses/compact`; [normalizeOpenAICompactRequestBody](../../../../../sub2api/backend/internal/service/openai_gateway_request_body.go) оставляет model/input/instructions/tools/parallel_tool_calls/reasoning/service_tier/text/previous_response_id и удаляет store/stream. Это описание серверного whitelist, а не разрешение AgentBridge отправлять continuation.

[resolveOpenAICompactFallbackModel/prepareOpenAICompactFallbackRetry](../../../../../sub2api/backend/internal/service/openai_compact_fallback.go) используют account compact-only mapping, затем Gateway.OpenAICompactModel; fallback может сработать при error либо failure shell. Обе forwarding ветки вызывают эту логику. [Stream bridge](../../../../../sub2api/backend/internal/service/openai_compact_stream_bridge.go) и [keepalive](../../../../../sub2api/backend/internal/service/openai_compact_sse_keepalive.go) допускают SSE; Accept JSON не доказывает unary body. Успешный ответ с восстановленным original model не доказывает сохранение фактической модели.

Уточнение: `Forward` строки405–410 и `forwardOpenAIPassthrough` строки138–149 используют resolved compact model **уже на первой отправке**. Это подтверждают исходные tests `TestOpenAIGatewayForwardUsesGlobalCompactModelOnInitialLegacyRequest` в [fallback tests](../../../../../sub2api/backend/internal/service/openai_compact_fallback_test.go) и ordinary/passthrough cases в [mapping tests](../../../../../sub2api/backend/internal/service/openai_compact_model_mapping_test.go). Go-тесты не запускались. Отключения только retry fallback недостаточно; нужен guard первоначальной модели, whitelist и discriminator, отдельно от ordinary generation.

До подтверждения профиля/mapping и canonical discriminator/items CompactAsync остаётся Unsupported. Не отправляется обычная generation вместо compact. Existing ContextCompactor/IDialogContextWriter сохраняют прежние Completed-only/save-before-activation/history правила; новая Sub2Api интеграция с ними не выполнена.

## Граница этапа04

Без доказанного происхождения encrypted reasoning/compact одинаковый model ID недостаточен. Transport нельзя открыть через custom settings, обходя T01. Текущий gateway отклоняет все generation/compact до HTTP, сохраняя input/continuation. Persisted connector provenance, legacy handling, restart и durable no-replay остаются04; эти работы не начинались. После снятия T01/T05 ещё нужны настоящие isolated Sub2Api JSON/SSE/tool/compact проверки и отдельно live OAuth приёмка05.03.

## Текущий путь: только клиентская адаптация

1. Использовать существующие routes и формы JSON/SSE, без предложенных vendor headers/processing metadata. Разобрать, какие existing manifest сведения можно честно отразить как объявленные, не приравнивая их к гарантированному input budget или provenance всего pool.
2. Разделить транспортные преобразования OAuth stream/store/SSE-to-JSON, обратимые tool/ID преобразования и потери canonical содержимого. Server retry не считать client retry. Проверять сохранность пар call/output, opaque и ordering на фактических обычной/passthrough ветках, а не требовать нового общего server enforcement API.
3. Existing passthrough — кандидат на более узкий поддерживаемый сценарий, но не автоматическое решение: shared prelude и compatibility normalizers действуют до/внутри него. В частности, `normalizeOpenAIResponsesCompatibilityBodyWithOptions` удаляет reasoning.content, может чистить orphan outputs/обрезать text и нормализовать schemas. Нельзя объявить encrypted/canonical preservation доказанным лишь по имени режима. Конфигурация целевого pool в этом запуске не проверялась; live/OAuth запрещены текущим поручением.
4. При отсутствии доступной actual-model metadata сохранять только реально объявленную response model; не выдавать её за independently verified upstream identity. Compact с неподтверждёнными моделью/discriminator остаётся Unsupported, без замены генерацией и без изменения сервера.
5. Проверить клиентскую границу бюджета: existing `ContextBudgetPolicy.ServerValidation` разрешает неизвестную стоимость opaque, но всё ещё требует известный `InputContextWindow`. `ModelSelectionValidator`, `ContextBudgetGuard`, `TurnModelSettings` используют положительное окно; просто выбрать ServerValidation недостаточно. Локальный операционный лимит и объявленный моделью budget — разные контракты. Их смешение или подмена null порогом запрещены. Если дальнейшее решение потребует изменить эти контракты либо provenance/persistence04, сначала назвать конкретную зависимость; не выполнять её скрыто в03.

Это направление не объявляет адаптацию уже реализованной и не закрывает T01/T05. Сейчас runtime guard сохранён. От пользователя не требуется согласовывать изменения sub2api: такой вариант исключён. Исследование/реализация продолжаются только в клиентских границах; конкретное противоречие исходным требованиям не подменяется требованием переделать сервер.
