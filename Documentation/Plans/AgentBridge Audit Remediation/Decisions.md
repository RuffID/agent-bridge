Документ дополняет исторический [OpenQuestions аудита](<../AgentBridge Quality Audit/OpenQuestions.md>). Старые результаты A и незапущенные B/C/D не переписываются. Решение о контракте не означает исправление кода или прохождение проверки.

## Q-002 — Окружение и поставка

- Основная БД ближайшего внедрения — **Microsoft SQL Server (MSSQL)**. PostgreSQL больше не является основным сценарием этого плана; уже реализованные PostgreSQL/SQLite сохраняются с адресной проверкой совместимости при изменении общего слоя.
- Сейчас разработка и проверки на **Windows11**, платформа **.NET10**. Целевое подключение — ASP.NET Core на Ubuntu Server.
- Библиотеку и её зависимости требуется поставлять для **win-x64, linux-x64, linux-arm64**. RID означает платформу приложения-потребителя; поддержка клиента Linux ARM64 не обещает запуск самого SQL Server Engine на ARM64.
- SQL Server backup строится на существующем модуле EFCoreLibrary и серверном backup/verification. `pg_dump`/`pg_restore` не входят в основной MSSQL-сценарий. BackupDirectory для SQL Server — каталог, доступный серверу БД и его служебной учётной записи, а не произвольный путь ASP.NET Core приложения.
- Live codex-lb проверяется позже: endpoint пока не задан. Допустим небольшой расход токенов; конкретный предел и операции задаются перед запуском. Это не разрешение на реальные вызовы сейчас.

**Состояние Q-002: частично определён.** Перед реальными проверками уточнить версии/редакцию SQL Server, Ubuntu, архитектуру тестовых машин, credentials/TLS, серверный backup path, собственные ресурсы/команды, deployed codex-lb/exact models и бюджет. Не заменять ARM64 runtime evidence сборкой на Windows.

## Q-003 — Текущие правила и старые задания

Основная `openspec/specs/agent-runtime/spec.md` описывает действующее поведение. Старые change/delta документы отражают историю разработки; промежуточный запрет compact не отменяет согласованное и реализованное сжатие. Нельзя применять такой запрет повторно при будущем sync.

**Неоднозначность Q-003 согласована.** В этапе09 нужно закрепить это в актуальном описании workflow, проверить доступным разрешённым CLI main и исходные18 changes, отдельно подготовить безопасное завершение старых заданий. CLI evidence ABQA-003 и actual синхронизация ABQA-004 пока не закрыты; архивирование автоматически не разрешено.

## Q-004 — Известные вложенные controls

AgentBridge до HTTP отклоняет неверные типы и повторные поля известных вложенных настроек с `Validation`. Например, известный `reasoning.summary` должен соответствовать его согласованной форме; число вместо строки/null и duplicate known `summary` не уходят на сервер.

Неизвестные вложенные поля сохраняются без переименования, удаления или нормализации. Поддержка конкретной модели проверяется локально только при подтверждённом контракте; неизвестные возможности не угадываются по статическому списку. Неизвестные top-level параметры по-прежнему регулируются существующим transport contract.

**Неоднозначность Q-004 согласована; реализация и проверки — этап10.** JSON/SSE/compact должны использовать одну согласованную границу validation. Достоверность исходного аудита не повышается задним числом.

## Q-005 — Вызовы и результаты при compact

Для повторного `call_id` используется единое правило FIFO: результат относится к первому ещё не закрытому вызову с этим ID. Сжатие сохраняет именно связанные occurrences «вызов → результат»; сокращение истории не меняет association.

Исходные canonical IDs/items не переименовываются; глобальная дедупликация по `call_id` запрещена. Если связь нельзя достоверно установить, сжатие явно отклоняется, исходная история и последнее принятое окно сохраняются. Отказ не разрешает повтор инструмента или догадку о связи результатов.

**Неоднозначность Q-005 согласована; local/server совместимость проверяется и при необходимости исправляется в этапе11.** Изменения codex-lb требуют отдельного поручения. Live evidence остаётся в этапе19.

## Настройки и простое подключение

Приложение создаёт и передаёт `IConfiguration` либо выбранный раздел. Оно само выбирает JSON-файлы, отдельный файл AgentBridge, environment variables, secret store и порядок объединения источников. Библиотека не открывает собственный config, не ищет `appsettings.json` и не хранит secrets.

`IConfiguration` используется в регистрации для binding и локальной проверки типизированных options. Прикладные сервисы получают соответствующие options, а не общий конфиг. Все обязательные для выбранного режима операционные параметры задаются явно: отсутствующий раздел, ключ, пустое или недопустимое значение вызывают безопасное исключение до первой операции. Скрытые значения по умолчанию для обязательных параметров не соответствуют новому контракту. Общий API key может отсутствовать при явно выбранном источнике индивидуальных ключей; инструкции могут поступать на обращение, если выбран такой режим.

Разделить три ограничения: мягкий объём истории в байтах; порог compact и запас полного входного бюджета в токенах; ограничения шагов и таймаутов. Не обещать лимит выходных токенов или точный opaque budget без поддержки текущего transport/model contract.

RetentionPeriod определяет срок жизни от создания диалога. **Расписание запуска очистки и размер пакета задаёт и исполняет приложение** из своего IConfiguration; DI не запускает фоновую службу. Настройки обязательны в рамках явно включённого режима очистки, не для приложения, которое его не подключает.

Логирование использует `ILogger` приложения. Приложение задаёт provider/Serilog sinks, путь, уровни, ротацию и срок хранения; при файловом логировании путь для событий AgentBridge задаётся явно в его конфигурации. Проверка наличия этого пути принадлежит регистрации логирования приложения; библиотека не создаёт logger/файл и не требует filesystem path от console/custom sink. Логи и backup имеют разных владельцев и разные пути.

Будущая общая регистрация относится к отдельному интеграционному слою, зависимому от ядра и адаптеров. Она собирает standard options/DI без HTTP/БД/hosting, миграций, собственного расписания или logger. Ядро не получает зависимости от ASP.NET Core и конкретных адаптеров. Authentication, owner/business authorization, индивидуальные keys, инструменты и собственные context providers остаются у приложения.

Плановые этапы12–15 реализуют MSSQL, строгую configuration boundary, короткую регистрацию и три RID. Их создание не является разрешением начать кодирование, generated migrations, builds или real integration.
