# Изолированные тесты

## Карта и зависимости

- `AgentBridge.Tests` проверяет ядро/Application и ссылается только на корневой production-проект.
- `AgentBridge.CodexLb.Tests` проверяет транспортный адаптер и ссылается на `AgentBridge.CodexLb`.
- `AgentBridge.Persistence.EfCore.Tests` проверяет адаптацию хранения и ссылается на `AgentBridge.Persistence.EfCore`.
- Тестовые зависимости: xUnit, Microsoft.NET.Test.Sdk и runner Visual Studio. Production-проекты не ссылаются на тесты, а корневой compile glob исключает весь каталог `tests`.
- Проверки конфигурации используют Microsoft.Extensions.Configuration с in-memory источником и обычный ServiceProvider. Публичная граница — групповые DI-расширения, options и явный `IStartupValidator`, без хоста. Секреты в fixtures только синтетические.

## Правила проверки

- Проверять значимое поведение и ошибки по мере реализации этапов. Не добавлять фиктивные тесты для пустых сборок или проверки констант проекта.
- Compile-check не запускает приложение или тесты. Обычный runner `dotnet test`/xUnit разрешён для изолированных unit-тестов без реальных интеграций; технический процесс тестового runner не считается запуском приложения.
- Не запускать приложение или библиотеку через hosting, TestServer, WebApplicationFactory и аналогичные механизмы. Такие проверки не относятся к изолированным unit-тестам.
- Использовать подставные порты, ответы и локальные потоки. Не обращаться к реальному HTTP, БД, SQL, Docker или внешним процессам; SQLite in-memory также не относится к проверкам без БД.
- Новые тесты размещать здесь, а не рядом с production-кодом; инфраструктура тестов не становится публичным API библиотеки.
- XML `<summary>` тестовых типов и методов писать на русском. Реализации интерфейсов в test doubles документировать `<inheritdoc/>`.
- Перед restore/build/test проверять конкретный `.csproj` и действующие build-файлы. Указывать точную команду, фактический результат и пропуски; успешную сборку не выдавать за пройденные тесты.
