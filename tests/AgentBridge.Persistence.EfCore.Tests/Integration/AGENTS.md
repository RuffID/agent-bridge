# Интеграционные проверки завершённых сценариев

## Актуализация схемы и migrations

- При добавлении/изменении migration любого provider в той же задаче обновлять IntegrationSchemaExpectations: точные ordered migration IDs и полный состав собственных таблиц. Fixtures Initialize/Update/Inspect/history и current-schema Down/Up/backup/restore проверки используют этот контракт, а не исторические количества 3/1 migrations или 6 таблиц. ProviderDesignTimeTests сверяет его с actual generated migration assemblies и current model без подключения к БД, чтобы isolated запуск обнаруживал рассинхронизацию integration expectations.
- Обязательно просмотреть все integration assertions/SQL selectors по migrations, history, таблицам и Down/Up targets даже при запрете запуска БД. Expected IDs/таблицы задаются явно; не вычислять expected из actual GetMigrations/model, не заменять strict проверки на NotEmpty/Contains/latest-only. Historical initial/downgrade targets и legacy cascade checks сохраняют свои исторические границы.
- Шесть legacy dialog tables в root-cascade fixtures не являются полным current schema: catalog/clock/feed/tombstone не каскадируют с root, recovery operations имеет отдельный cascade FK. Full-schema проверки охватывают все десять таблиц; legacy data fixtures не выдавать за registered catalog/recovery SQL acceptance.
- После актуализации выполнить compile-check и isolated metadata tests. Если Database tests запрещены или не запускались, прямо записать это в evidence; isolated green не означает integration green. Повторный запуск реальной БД требует разрешения в текущей сессии, если её ограничения строже исторического разрешения ниже.

- MSSQL адресные проверки проходят actual write ports/UoW: два Serializable writer одного root (typed Conflict отдельно от SqlException1205, включая штатную InvalidOperationException-обёртку SqlServerExecutionStrategy без retries; произвольные/cleanup ошибки — failure), rollback после real SaveChanges до commit, cascade всех шести таблиц и неизменный соседний диалог. Barrier координирует реальные root SELECT обоих providers; session decorator делегирует actual EFCoreLibrary save/transaction и только затем вводит отказ.
- MSSQL maintenance проверяет real native copy-only/checksum backup до migration, полный backup текущей схемы с данными шести legacy-таблиц и restore в отдельную новую abverify_<GUID N> БД, DDL failure2714 с исходным SqlException и poisoned shared gate. Restore выполняется через existing IDatabaseCommands с FILELISTONLY/MOVE/CHECKSUM, без отдельного production pipeline; fingerprint сравнивает таблицы/колонки/индексы/default/check/FK и все строки, включая history/settings. После failure backup находится в реальном msdb, подтверждается HEADERONLY/VERIFYONLY и восстанавливается; подставной receipt не используется. Все БД, физические data/log и backup принадлежат контейнеру коллекции и удаляются вместе с ним.

- ActualMigrationFailurePoisonsSharedGateAndPreservesBackup проверяет исходную ошибку DDL в InnerException: SqliteException с SqliteErrorCode=1 либо PostgresException с SqlState=42P07. Maintenance-код MigrationFailed, poisoned gate и восстановимость backup проверяются отдельно.

- MSSQL запускается автоматически только через `DatabaseIntegrationFixture.CreateSqlServerDatabaseAsync`: коллекция владеет одним ленивым `SqlServerIntegrationFixture` с Testcontainers.MsSql 4.14.0 (только тестовая зависимость). Образ `mcr.microsoft.com/mssql/server:2022-CU20-ubuntu-22.04`, Developer edition, случайный loopback-порт, UUID-имя и временный пароль sa. SQLite/PostgreSQL и isolated-набор не строят и не запускают MSSQL. `SqlServerIntegrationFact` не имеет Skip; `AGENTBRIDGE_SQLSERVER_*` не используются.
- Подготовка контейнера, включая pull/readiness/backup каталог, ограничена тремя минутами и отменой теста. Failed/cancelled startup остаётся единственной попыткой; нет skip/fallback/restart/retry. Readiness polling Testcontainers не повторяет подготовку. Raw ошибки Docker/exec и logger контейнера подавлены ради пароля в sqlcmd; безопасная ошибка сохраняет тип и контекст, cleanup failure остаётся падением.
- Settings формируется из опубликованного порта и connection контейнера: exact `tcp:127.0.0.1,port`, уникальная новая БД `abverify_<GUID N>`, Encrypt=Mandatory, явный TrustServerCertificate=true для временного самоподписанного сертификата, Pooling=false/ConnectRetryCount=0/ConnectTimeout=15, стабильный endpoint и maintenance budget две минуты. Backup каталог `/var/opt/mssql/abverify_<GUID N>` создаётся внутри контейнера с mode700; проверяются запись и uid10001 (mssql). Внешние bind mounts/volumes не подключаются.
- `SqlServerIntegrationDatabase` владеет только DI; InitializeNewAsync вызывает реальные CREATE/migration через maintenance EFCoreLibrary. Restart в `SqlServerPersistenceIntegrationTests` означает новый DI root, без рестарта SQL Server. Контейнер коллекции удаляется после успеха/ошибки/отмены вместе с БД и backup-файлами, независимо от отменённого токена теста; ошибки удаления не скрываются. Владение задаётся объектом созданного контейнера, не поиском по префиксу. Isolated Settings/FixtureTests проверяют parsing/metadata/lazy lifecycle/sticky failure/cancellation/cleanup без Docker, SQL и соединений.

- CrossComponentFixture/Tests23 использует actual runner, catalog/JSON/SSE/compact adapter, HttpClientLibrary, offline BPE и EFCoreLibrary CRUD/UoW. ScriptHandler не обращается к сети и падает на лишнем запросе. Scoped handler наблюдает committed Started отдельным parent-aware query до действия; собственный пустой DbContext наблюдателя не доказывает отсутствие чужой транзакции.
- Сквозной backup/restore23 использует настоящие native SQLite/pg_dump/pg_restore через существующий fixture, сопоставляет всю схему и данные включая journal/settings/turn snapshot/compact provenance. Synthetic acknowledgement failure после actual outcome writer success не является реальным сетевым сбоем. Временные gates всегда освобождаются и tasks ожидаются в finally.

- ExpiredDialogCleanupIntegrationTests22 проходит public app-invoked orchestration → actual base CRUD/deletion UoW, equality/bounded packages/cascade включая DialogSettings, partial failure/cancel после настоящего SQL SaveChanges до commit и cleanup-vs-active-run/recreate. Sources/gateway управляемые, HTTP/hosting нет; actual offline BPE используется runner. Stale revision моделируется исторической pre-expiry записью между read/delete: не доказательство late write. Таблицы Dialogs и DialogSettings используют колонку Id, остальные — DialogId. Старые maintenance/backup/restore не повторять без нового риска.

- DialogSettingsIntegrationTests21 добавляет адресные actual settings/provenance риски на EFCoreLibrary0.0.5: independent version не ломает активный runner token, новый run/override, restart, atomic rollback, cascade/guards, first insert и update concurrency. Typed stale/CAS Conflict отличать от busy/serialization driver errors без retry. Down/Up21 сохраняет canonical history и ContentBytes содержимого, но settings/provenance намеренно теряются и возвращаются null.

- Пользователь разрешил автоматические SQLite/PostgreSQL/MSSQL интеграционные тесты с собственными временными файлами, БД, backup и Testcontainers через локальный Docker Desktop, включая настоящие pg_dump/pg_restore; повторное разрешение и переключатель окружения не требуются. Внешние/рабочие БД, чужие контейнеры/volumes, изменение Docker Desktop, приложение/hosting и deployment запрещены. Исторический набор00–13 не выдавать за evidence EFCoreLibrary0.0.5. AgentRunnerIntegrationTests20 проверяет адресные новые durable risks через actual runner/write ports; весь maintenance без новых рисков не повторять.
- Runner20 tests подтверждают separate-scope Started до handler, атомарность journal+outputs при реальном SQL rollback, lost acknowledgement после real commit, legacy/restart no replay, guards/late delete/cleanup/expiry и новые migration Down/Up с historical rows. Parallel observer использует один parent-aware base query committed step; multi-read DialogReader вправе дать Conflict при соседнем checkpoint и не должен получать retry ради теста.
- `Dependency=Database` отделяет проверки от изолированного набора. `DatabaseIntegrationTheory`/`SqlServerIntegrationFact` сохраняют источник теста для xUnit без условного Skip. Окружение создаётся автоматически при запуске; переменные включения не используются. Недоступный Docker или утилиты дают ошибку, не skip.
- `DatabaseIntegrationCollection` отключает параллельность и получает один `DatabaseIntegrationFixture`. Fixture создаёт собственный UUID-каталог в temp; SQLite получает отдельные файлы без запуска Docker. Первый PostgreSQL-case через Testcontainers.PostgreSql запускает один `postgres:18` с готовностью не более двух минут, случайным loopback-портом, собственным пользователем/паролем и bounded tmpfs без пользовательских volumes. Fsync/full_page_writes/synchronous_commit включены явно: модуль Testcontainers по умолчанию отключает durability. Failed startup не повторяется. Testcontainers может использовать служебный Ryuk для очистки собственных ресурсов.
- Каждый тест получает `IntegrationDatabase` через `fixture.CreateDatabaseAsync`; новые тестовые БД независимы, миграции по-прежнему явно применяются настоящим maintenance API. Имена БД и пользователя начинаются с `abverify_`. Рабочие секреты, внешние подключения и существующие БД запрещены. `AGENTBRIDGE_INTEGRATION_ROOT`, `AGENTBRIDGE_POSTGRES_CONNECTION` и `AGENTBRIDGE_PG_MAJOR` больше не используются этим набором; fixture не меняет process environment.
- Для PostgreSQL требуются настоящие pg_dump/pg_restore major 18 на Windows runner. `PostgreSqlIntegrationTools` ищет их в реестре PostgreSQL 18, Program Files и PATH; optional абсолютные `AGENTBRIDGE_PG_DUMP`/`AGENTBRIDGE_PG_RESTORE` имеют приоритет. Неверный explicit override или версия дают ошибку без fallback. Проверка `--version`, backup и restore идут через штатный process runner EFCoreLibrary; Docker exec и заглушки backup не заменяют production pipeline.
- Операции данных идут через публичные порты AgentBridge и реальные base repositories/scope EFCoreLibrary. SQL для наблюдения схемы и создания отказных условий — через IDatabaseCommands этой библиотеки; не заменять production pipeline.
- Миграции применяются настоящим maintenance API. Для проверки Down используется штатный IMigrator из DatabaseFacade библиотечного IUnitOfWorkContext, поскольку maintenance API не предоставляет downgrade.
- Backup выполняет реальный provider EFCoreLibrary. SQLite восстанавливается её native backup API, PostgreSQL — штатным pg_restore через её process runner. Restore всегда в отдельной тестовой БД, с сопоставлением схемы и данных.
- Сверять API с EFCoreLibrary 0.0.5: contracts — `.Maintenance.Abstractions`, models — `.Models`, budget — `.Coordination`, errors — `.Errors`, workspace — `.Backup`, commands — `.Database`, SQLite native API — `.Sqlite.Backup`, PostgreSQL provider — `.PostgreSql.Providers`. Integration должна компилироваться; сборка не разрешает её запуск.
- Каждый database fixture владеет только созданными им файлами/БД и очищает их при DisposeAsync. Collection fixture владеет контейнером, удаляет его после тестов и удаляет только пустой собственный root; ошибки cleanup не скрываются. При unconfirmed disposal файлы сохраняются. Тестам разрешено автоматически создавать и удалять только собственное Testcontainers-окружение; вручную контейнер готовить не требуется. Restore/build/test всегда с GeneratePackageOnBuild=false, outputs и credentials не коммитить.

## Запуск SQLite/PostgreSQL

Нужны Windows, запущенный локальный Docker Desktop с Linux containers и клиентские утилиты PostgreSQL 18. Из PowerShell в корне репозитория:

```powershell
dotnet test --project tests/AgentBridge.Persistence.EfCore.Tests/AgentBridge.Persistence.EfCore.Tests.csproj -c Debug -p:GeneratePackageOnBuild=false --filter-class '*AgentRunnerIntegrationTests' --filter-method '*DurableStartEnforcesGuards*'
```

Этот адресный запуск выполняет десять реальных случаев SQLite/PostgreSQL. Для всех классов SQLite/PostgreSQL используйте `--filter-trait 'Dependency=Database' --filter-not-class '*SqlServerPersistenceIntegrationTests'`. В Visual Studio достаточно запустить тесты при готовом Docker Desktop; переменные включения не нужны.

## Сборка, изолированные проверки и MSSQL

Для MSSQL нужны Windows runner и локальный Docker Desktop с Linux containers; ручной сервер, внешние БД и переменные `AGENTBRIDGE_SQLSERVER_*` не нужны. PostgreSQL-утилиты при адресном MSSQL запуске не проверяются. Из корня репозитория:

```powershell
dotnet restore tests/AgentBridge.Persistence.EfCore.Tests/AgentBridge.Persistence.EfCore.Tests.csproj -p:GeneratePackageOnBuild=false
dotnet build tests/AgentBridge.Persistence.EfCore.Tests/AgentBridge.Persistence.EfCore.Tests.csproj -c Debug --no-restore -p:GeneratePackageOnBuild=false -p:BaseOutputPath=.\artifacts\compile-check\
dotnet test --project tests/AgentBridge.Persistence.EfCore.Tests/AgentBridge.Persistence.EfCore.Tests.csproj -c Debug --no-build --no-restore -p:GeneratePackageOnBuild=false -p:BaseOutputPath=.\artifacts\compile-check\ --filter-not-trait 'Dependency=Database'
dotnet test --project tests/AgentBridge.Persistence.EfCore.Tests/AgentBridge.Persistence.EfCore.Tests.csproj -c Debug --no-build --no-restore -p:GeneratePackageOnBuild=false -p:BaseOutputPath=.\artifacts\compile-check\ --filter-class '*SqlServerPersistenceIntegrationTests'
```

После реального запуска сверять отсутствие созданных тестом контейнеров и собственных временных каталогов; не удалять чужие ресурсы и не выполнять Docker prune. Первый запуск может скачать образ; это не запуск приложения или hosting.
